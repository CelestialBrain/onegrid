# oneGrid v0.0.7 — Implementation Patterns Report

This report documents the implementation patterns the oneGrid v0.0.7 milestone converged on for nine cross-cutting concerns. It is restricted to *patterns* — every recommendation is sourced from public W3C/WHATWG specs, MDN, RFCs, browser-engine bug trackers, and individual-engineer writing. No commercial data-grid source, prose, or trademark is referenced.

Unlike v0.0.6 which was written before the milestone landed, this report is post-hoc: each section ends with a `Code surface in oneGrid` block that points at the *actual* paths shipped on `main`, and "Test strategy" describes the gates that are wired in CI today.

---

## 1. Tree data with lazy-load children

**Architecture.** Tree mode is a thin layer over the existing `getRowMeta` / `onToggleGroup` channel that already drives row grouping — so the renderer's chevron-click hit zone, the ARIA shadow's outline semantics, and the keyboard-navigation pipeline don't need a parallel code path. The data layer (`@onegrid/data`) supplies a pure-sync `flattenTree(roots, openIds) → FlatTreeEntry[]` helper that walks the open set top-down. Lazy-load is signalled by an optional `loadChildren?: () => Promise<TreeNode[]>` on each node; the data layer never invokes it — the *caller* runs the async fetch on `onToggleGroup`, then rebuilds the row source. This keeps the data layer deterministic and lets framework adapters drive their own loading-state UX.

The row meta union is widened to a discriminated `RowGroupMeta | RowTreeMeta`. Tree rows carry `depth`, stable `id`, `expanded`, `isLeaf`, and `hasChildren`. The renderer indents the leftmost cell by `depth * 16` pixels and paints a chevron when `hasChildren` — so a tree node that hasn't loaded yet still gets a chevron, and the click triggers the lazy fetch.

**Edge cases**
- Stable identity vs rebuilt rowSource: `useOneGrid` triggers `setRowSource(...)` on every identity change, so the playground's tree-mode helper rebuilds its `RowSource` after every toggle (rather than mutating in place) to ensure the imperative path fires (otherwise `numRows` and Fenwick heights drift out of sync with the live flat list).
- Async children that resolve after the user collapsed the parent: the cached children stay in memory; the next expand reuses them. Cache eviction is the caller's call.
- Tree rows ARE selectable per cell — unlike group rows, which are a banner with no per-column data. Cell renderers must therefore continue to render on tree rows (they're skipped only for `kind === 'group'`).
- Master-detail and tree mode coexist on the same `getDetailContent` API. The chevron column overlay (master-detail) and the depth-indented chevron (tree) live at different x-bands so they don't collide.

**Test strategy**
- Unit (vitest, `packages/data/src/__tests__/tree.test.ts`): 7 cases covering collapsed roots, single-level expand, recursive expand, lazy `hasChildren` rendering before fetch, open-empty-lazy state, `countTreeNodes`.
- Browser (Playwright, `apps/benchmarks/src/tree.spec.ts`): 3 cases — tree mode mounts with 3 collapsed roots, chevron click reveals children, lazy-loaded country (Brazil) fetches on first expand and the row count grows post-resolution.

**Code surface in oneGrid**
`packages/data/src/tree.ts` (`flattenTree`, `TreeNode`, `FlatTreeEntry`, `countTreeNodes`), `packages/core/src/types.ts` (`RowTreeMeta` discriminator), `packages/core/src/grid.ts` (chevron hit zone in `handlePointerDown`, indent + chevron in `drawRows`), `apps/playground/src/lib/tree-mode.ts` (synthetic regions/countries/cities dataset with a 600 ms async loader on Brazil).

**References:** https://www.w3.org/WAI/ARIA/apg/patterns/treegrid/ · https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/treegrid_role

## 2. Nested grids inside detail panels

**Architecture.** A oneGrid instance mounted inside another grid's detail panel must respect three lifecycle invariants: (a) the inner grid's `destroy()` is called when the panel is unmounted (otherwise the inner canvas + ResizeObserver + ARIA shadow leak), (b) focus / scroll gestures inside the inner grid don't escape to the outer grid's pointer-event listeners, and (c) rebuilding the outer grid's rowSource doesn't tear down inner instances unnecessarily. Pattern (a) is solved with a new `Grid.onDetailUnmount(rowIndex, el)` callback that fires *before* the panel leaves the DOM (collapse OR scroll-out OR outer destroy) — the consumer reads their inner Grid back off the panel element via a stashed key (`__innerGrid`) and calls `destroy()` on it. Patterns (b) and (c) fall out of the existing master-detail layer's pointer-events:none host + per-panel `pointer-events:auto` children.

Master-detail panels render through Grid's own DOM detail layer; the canvas behind them keeps painting. Inner Grids don't need clip / overflow magic because `getDetailContent` returns an HTMLElement that the Grid positions absolutely inside the layer.

**Edge cases**
- Initial layout: the inner host has size 0 at `getDetailContent` return time (the parent panel hasn't been positioned yet). The Grid uses a ResizeObserver, so the inner canvas resizes as soon as the browser flushes layout — no manual measurement needed.
- Outer destroy without collapsing first: `Grid.destroy()` iterates `mountedDetails` and fires `onDetailUnmount` for each panel before clearing the map, so consumers don't need to track which panels are still open.
- Selection independence: each grid has its own `SelectionModel`. Pointer events on the inner grid's `scrollHost` don't bubble into the outer grid's pointerdown handler because the outer's listener is bound to the *outer's* scrollHost, not the host element.
- Multiple expanded rows = multiple inner grids; each survives independently. The Playwright spec asserts this by expanding two rows and counting `div[role="grid"]` (outer + 2 inner = 3).

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/master-detail.spec.ts`): 3 cases — chevron expand mounts the inner grid (page has 2 div[role="grid"] hosts), collapse destroys it (back to 1), expanding multiple rows mounts a separate inner grid per row (3 total).
- Live verification (Chrome DevTools MCP): every developer-facing change is verified in real Chromium before commit, per the project's hard-learned rule that jsdom misses canvas + WebGPU + IntersectionObserver behaviour.

**Code surface in oneGrid**
`packages/core/src/types.ts` (`onDetailUnmount` option), `packages/core/src/grid.ts` (`syncDetailLayer`, `destroy()`), `packages/adapters/react/src/use-one-grid.ts` (ref-based callback wiring), `apps/playground/src/App.tsx` (audit-log inner grid factory).

**References:** https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver · https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver

## 3. Server-side hierarchical fetches (SSRM tree)

**Architecture.** The SSRM contract gains exactly two additions: an optional `parentId?: string | null` on `BlockRequest` (null = root level, undefined = flat-mode, string = children of that node) and an optional per-row `hierarchy?: HierarchyEntry[]` on `BlockResponse` aligned with `rows`. `parentId` participates in the cache *fingerprint* — so blocks fetched under parent A don't collide with blocks fetched under parent B, and changing parent doesn't invalidate the rest of the tree's cached blocks. Adapters that don't care about hierarchy ignore both fields; the protocol stays backwards-compatible.

Client-side, `createSsrmTreeSource(dataSource, opts)` is a new RowSource factory that exposes the same synchronous `RowSource` shape the canvas needs, but its internal state is a `Map<parentId, CachedChildren>` plus a `Set<openIds>`. On `toggle(id)`: if children aren't cached, kick off `fetchBlock({ parentId: id, ... })`; rebuild the flat view; call `onUpdate` (which the playground translates into `grid.setRowSource(handle, 28)` so Fenwick + aria-rowcount track the growing list). The mock server demonstrates this against a synthetic regions → countries → cities dataset, showing the round-trip fully exercises wire encoding.

**Edge cases**
- Distinct cursor spaces per parent: a cursor returned for parent A is NOT valid against parent B. The protocol comment makes this explicit; the BlockCache key for a root-level block must never collide with a children block under any parent.
- Async-during-collapse: collapsing a node mid-fetch is fine — the children land in the cache and the flat view stays unchanged. Re-opening shows them with no second fetch (cache hit).
- `numRows` growth between renders: the wrapped RowSource has a *live getter* for `numRows`; the playground re-calls `setRowSource(...)` on every `onUpdate` tick to rebuild Fenwick rather than relying on the renderer to detect length changes (Fenwick is constructed from `rowSource.numRows` once at `setRowSource` time).
- Awaited initial root fetch: the playground's `connectSsrmTree` resolves only after the first onUpdate fires, so the Grid mounts with non-empty rows on the first render and `useOneGrid` doesn't skip mounting via its `numRows === 0` guard.

**Test strategy**
- Unit (vitest, `packages/ssrm/src/__tests__/tree-source.test.ts`): 7 cases — root fetch on construct, toggle fetches children, leaf-toggle no-op, collapse/re-open hits cache, nested cascade, `parentId` in wire request, `invalidate` forces re-fetch.
- Browser (Playwright, `apps/benchmarks/src/ssrm-tree.spec.ts`): 3 cases against the real mock server — 3 collapsed roots, EMEA expansion → 5 rows, Germany expansion → 7 rows.

**Code surface in oneGrid**
`packages/protocol/src/index.ts` (`BlockRequest.parentId`, `HierarchyEntry`), `packages/ssrm/src/fingerprint.ts`, `packages/ssrm/src/cache.ts` (key derivation), `packages/ssrm/src/tree-source.ts`, `apps/ssrm-mock-server/src/server.ts` (hierarchical dataset + `/tree-schema` endpoint), `apps/playground/src/lib/ssrm-tree.ts`.

**References:** https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html (cursor / `$skiptoken` semantics) · https://www.postgresql.org/docs/current/queries-with.html (recursive CTEs)

## 4. Column drag-drop reorder

**Architecture.** Column reorder lives entirely in the Grid's pointer-event pipeline. Header pointerdown captures a *drag candidate* (column index + initial clientX); a movement of `> 6 px` promotes it to an active drag with a vertical drop indicator (a div lazy-mounted as a child of the host, `pointer-events: none`, snapping to the nearest column boundary); pointerup with no movement fires `onHeaderClick` (so a tap still toggles sort), and pointerup after a drag splices the live `columns` array in place and fires `onColumnReorder(from, to, id)`. The drop indicator's x-coordinate respects the frozen vs scrollable bands — frozen-zone boundaries don't shift with horizontal scroll, scrollable-zone boundaries do.

The crucial architectural choice is that `columns` is now *mutable internally* — copied from the consumer's array at construction so their reference is untouched, but spliced in place on drop so scroll position and selection survive without a Grid teardown / remount cycle. Consumers can mirror the change in their own state via the callback if they need persistence across re-mounts.

**Edge cases**
- `setPointerCapture` on the scrollHost so the cursor leaving the grid bounds doesn't drop the drag. Wrapped in try/catch because some browsers refuse capture during certain events; the global `window` pointerup listener provides a safety net.
- Click-vs-drag disambiguation: under-threshold pointerdown→pointermove→pointerup is treated as a click, so the legacy onHeaderClick (sort) UX is preserved on touch devices that wobble slightly.
- Cross-zone drag: dragging from a frozen column to a scrollable position is permitted; consumers who want to forbid it can revert via the callback.
- Column groups / column-tool-panel ordering: the column-group band's index ranges are not auto-adjusted on reorder (a known v0.0.8 limitation — column groups currently break visually when reordered through them). The tool panel's separate drag pipeline does its own splice + setColumns call.

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/column-reorder.spec.ts`): 3 cases — pure click → sort still applies, drag → header order changes, sub-threshold drag → treated as click.

**Code surface in oneGrid**
`packages/core/src/grid.ts` (drag-candidate state + `handlePointerDown` + `handlePointerMove` + `handlePointerUp` + `ensureDragIndicator` + `updateDragIndicator`), `packages/core/src/types.ts` (`enableColumnReorder`, `onColumnReorder`), `packages/adapters/react/src/use-one-grid.ts`.

**References:** https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture · https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events

## 5. Column tool panel / sidebar

**Architecture.** The tool panel is a React component (`<ColumnToolPanel grid={grid} />`) layered on top of two new core APIs: `Grid.setColumns(columns)` and `Grid.getColumns()`. Together they replace the old "remount the grid to change columns" pattern with an in-place reorder/hide/show that preserves scroll position and (by id) selection. The panel reads the live column array from `grid.getColumns()` on mount, layers a panel-local `hidden` flag on top, and on every toggle / drag-drop reorder calls `grid.setColumns(visibleSubset)`.

Hidden columns are kept in panel-local state so re-showing them puts them back where they were, in their original order — without that, hide-then-show would shuffle the column to the end.

**Edge cases**
- Selection by index shifts when columns hide/reorder. This is documented; v0.0.8 will move to id-based selection internally.
- Panel mounts while `useOneGrid` hasn't resolved yet (`grid={null}`); the component renders an empty list and re-syncs on the next render once the grid lands.
- Interplay with the in-grid drag-drop reorder: the panel is the authoritative source while open; if the user drags a column header at the same time, the panel's next render diverges. Documenting this trade-off — both flows ultimately converge on the live `Grid.columns` array, so a re-mount of the panel snaps it back into sync.
- HTML5 drag events are used inside the panel for reorder; they don't compose with the canvas pointer pipeline (which is fine because the panel is DOM, not canvas).

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/column-panel.spec.ts`): 3 cases — opening the panel mounts one checkbox per column, unchecking hides the column from the live grid, re-checking restores it.

**Code surface in oneGrid**
`packages/core/src/grid.ts` (`setColumns`, `getColumns`), `packages/adapters/react/src/column-tool-panel.tsx`, `apps/playground/src/App.tsx` (toolbar toggle).

**References:** https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API · https://www.w3.org/WAI/ARIA/apg/patterns/listbox/

## 6. Context menu

**Architecture.** Right-click on the grid host fires `contextmenu`. The Grid's listener resolves the click target into a discriminated `ContextMenuTarget` (`{ kind: 'cell', rowIndex, columnId, clientX, clientY }` | `{ kind: 'header', columnId, clientX, clientY }` | `{ kind: 'empty', clientX, clientY }`), calls `event.preventDefault()` to suppress the browser's native menu, and forwards the payload via `onContextMenu(target)`. Rendering the popover is the consumer's responsibility — different platforms / styling systems / focus-trap policies make a one-size-fits-all menu component the wrong abstraction for the framework-agnostic core.

The playground ships a sample `<ContextMenuPopover>` React component with light dismiss (click-outside + Escape) and target-aware action lists: cell menus offer Copy / Sort / Hide, header menus offer Sort / Hide, empty menus show a placeholder.

**Edge cases**
- Touch devices: `contextmenu` may not fire at all on iOS Safari without a long-press; the fallback is a custom long-press handler the consumer wires (not in v0.0.7).
- Anchoring at the click position: `position: fixed; left: clientX; top: clientY` is sufficient for desktop; consumers wanting viewport-clamped placement can use Floating UI middleware (the same stack the tooltip uses in v0.0.6).
- Focus management: the playground's popover doesn't focus-trap. Real apps may want to (especially for keyboard-only users); WAI-ARIA's menu pattern documents the contract.

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/context-menu.spec.ts`): 4 cases — cell menu shows Copy/Sort/Hide, header menu omits Copy, Escape dismisses, click-outside dismisses.

**Code surface in oneGrid**
`packages/core/src/types.ts` (`ContextMenuTarget`, `onContextMenu`), `packages/core/src/grid.ts` (`handleContextMenu`), `packages/adapters/react/src/use-one-grid.ts`, `apps/playground/src/App.tsx` (`ContextMenuPopover`).

**References:** https://www.w3.org/WAI/ARIA/apg/patterns/menu/ · https://www.w3.org/WAI/ARIA/apg/patterns/menubar/

## 7. Sticky group rows + aggregation-aware pin

**Architecture.** When the user scrolls a grouped grid past the start of a group, that group's title row is repainted at the top of the data band so the user keeps the "what group am I in" context. The render pass adds a single `drawStickyGroupRow(visibleStart)` call after `drawHeader`: it walks backwards from the un-overscanned topmost-visible row to find the nearest ancestor group whose `y + h <= scrollTop`, then re-renders that row at `y = dataBandTop()` via the existing `drawGroupRow` path — so the sticky band's chevron, label, and per-column aggregates are pixel-identical to the inline version.

The walk uses the *un-overscanned* topmost row index, not the overscanned `start`, because overscan can include rows above the actual viewport edge and would cause the function to find the still-visible group row (and skip drawing the sticky one) at scroll offsets where overscan reaches above the data top.

**Edge cases**
- Single-level only: tree mode with depth > 1 currently pins exactly one ancestor (the immediate group). Multi-level sticky stacking is a v0.0.8 follow-up.
- Sticky band drawn AFTER `drawHeader` and AFTER cell rendering, but a per-band canvas clip prevents bleeding into the header chrome.
- Default-on when `getRowMeta` is set: `stickyGroupRows ?? options.getRowMeta !== undefined`. Consumers can opt out with `stickyGroupRows: false`.
- Aggregates render with horizontal-scroll offset preserved, so the sticky band's `Σ revenue $9.99B` columns track the underlying data columns as the user scrolls horizontally.

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/sticky-group.spec.ts`): 2 cases — pixel at the data-band-top is the group-row background `#1b1f26` after scrolling past, and is NOT that color when grouping is off.

**Code surface in oneGrid**
`packages/core/src/grid.ts` (`drawStickyGroupRow`), `packages/core/src/types.ts` (`stickyGroupRows`).

**References:** https://www.w3.org/TR/css-position-3/#sticky-positioning (semantic analogue, even though the implementation is canvas-painted) · https://www.w3.org/WAI/ARIA/apg/patterns/treegrid/

## 8. Range fill-handle

**Architecture.** A small 6×6 `#6ea8fe` square paints at the bottom-right of the *last* selection range. Pointerdown inside the handle's hit zone (with a 2px tolerance) captures a *fill-drag* with the source NormalizedRange + the current target cell; pointermove updates the target via `cellAtClient` and re-renders a dashed-outline preview of the union (source ∪ target rectangle); pointerup fires `onFillHandle(source, fill)` so the consumer applies the data policy — copy, linear interpolation, sequence, or whatever they decide. The Grid itself never mutates data; it owns the gesture, not the policy. Post-drop the live selection is extended to span the union so the user sees their commit highlighted.

The handle's hit detection has higher priority than master-detail / group chevrons in `handlePointerDown` (the rectangles don't overlap in practice, but the dispatch order matters when frozen + chevron-column widths align).

**Edge cases**
- The handle is drawn as a flat-fill square (no stroked dark border) so a pixel-cluster scan in CI can find it via density without confusing it with a cell border corner. (An earlier draft had a 1px dark outline; CI flake from finding the cell-border corner instead led to dropping it.)
- Drag below the current viewport: the cursor leaves the grid host; the global `window` pointerup listener still fires, finalising the drag without the user needing to release inside the grid.
- The fill rectangle reported to the consumer is the bounding *union* (source ∪ target), matching Excel's behaviour. The consumer subtracts the source if they want only the new cells.
- Source rect tracks a single NormalizedRange; multi-rect selections fall back to the last range, also matching Excel.

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/fill-handle.spec.ts`): 1 case — locate the handle by scanning the canvas for the densest #6ea8fe cluster, drag it 6 rows down, verify the seed value (row 0 score = 0) was copied into the new cells.

**Code surface in oneGrid**
`packages/core/src/types.ts` (`enableFillHandle`, `onFillHandle`), `packages/core/src/grid.ts` (handle draw + drag preview + pointer pipeline), `packages/adapters/react/src/use-one-grid.ts`, `apps/playground/src/App.tsx` (Excel-style copy handler).

**References:** https://support.microsoft.com/en-us/office/fill-data-automatically-in-worksheet-cells-74e31bdd-d993-45da-aa82-35a236c5b5db (UX reference — fill-handle behaviour described in the public help page; no source consulted)

## 9. Selection-checkbox column

**Architecture.** `createSelectionCheckboxColumn({ checkedRows, onChange })` returns a ColumnDef whose per-cell renderer is a React `<input type="checkbox">` wrapped via the existing `createReactCellRenderer` pool. Each cell subscribes to a *module-scoped store keyed by column id* via `useSyncExternalStore`, so the visible checkboxes re-render when the consumer passes a fresh `checkedRows` Set in — without a Grid remount, and without the renderer pool's `update()` short-circuit (which only re-renders on `(value, row, col)` identity change) blocking the visual update. The store pattern is the only viable bridge: the Grid's renderer pool cannot accept extra props per cell, and React Context can't cross the per-cell `createRoot` boundary the pool establishes.

The companion `<SelectAllCheckbox>` is a tri-state HTML `<input>` (`checked` / `indeterminate` / `unchecked`) for the toolbar — consumers drop it next to the grid; it shares the same `checkedRows` / `onChange` state.

**Edge cases**
- Group rows: a fix in `syncCellOverlay` skips per-column renderers for `kind === 'group'` rows. Without it, the checkbox `<input>` mounts on top of group banners and intercepts the chevron-click pointer path. Tree rows continue to render normally — they DO have per-column data.
- Synthetic column id: the playground's materialized `ColumnTable` throws on unknown columns. A wrapper around the rowSource swallows lookups for ids starting with `__onegrid_` (the convention for synthetic columns) and returns null, so `getCell(row, '__onegrid_select__')` doesn't crash the renderer pool.
- Frozen-column shift: enabling the checkbox column adds a frozen slot. The playground gates this behind a "Selection col" toolbar toggle (off by default) so the rest of the test suite — which pins coordinates against the original column layout — keeps passing.
- Visible cells re-render on Set change but not on every parent React render: `useSyncExternalStore` snapshots the Set reference, so unrelated re-renders don't trigger checkbox cell churn.

**Test strategy**
- Browser (Playwright, `apps/benchmarks/src/selection-checkbox.spec.ts`): 3 cases — visible row count of `<input>` checkboxes, ticking 3 rows updates the SelectAll label to "3 of 1000000 selected", SelectAll → 1M.

**Code surface in oneGrid**
`packages/adapters/react/src/selection-checkbox-column.tsx` (`createSelectionCheckboxColumn`, `<SelectAllCheckbox>`, the module-scoped subscription store), `packages/core/src/grid.ts` (group-row skip in `syncCellOverlay`), `apps/playground/src/App.tsx` (toolbar toggle + rowSource wrapping).

**References:** https://react.dev/reference/react/useSyncExternalStore · https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/ · https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA8.html (tri-state checkbox semantics)

## Critical-path implementation order (as shipped)

The v0.0.7 sequence ran in the order documented in `ROADMAP.md` — hardest-to-retrofit first:

1. **Tree data with lazy-load children** — first, because every later v0.0.7 item presumes the row-meta union extension exists.
2. **Nested grids inside detail panels** — second, builds on the tree-data row model AND the existing master-detail layer.
3. **Server-side tree expansion** — third, locks the protocol shape (`parentId`, `HierarchyEntry`) so v0.0.8 database adapters inherit a tree-aware `BlockRequest` instead of needing a v0.0.8.1 protocol break.
4. **Column drag-drop reorder** — fourth, locks the pointer-event hit-test plane so the renderer-touching items below don't have to redo pointer plumbing.
5. **Column tool panel** — fifth, slots onto the imperative `setColumns` API the column-reorder work landed.
6. **Context menu** — sixth, reuses the column-tool-panel React patterns.
7. **Sticky group rows** — seventh, smaller surface, slots onto the existing row-grouping infrastructure once renderer-touching items above settle.
8. **Range fill-handle** — eighth, composes on top of selection without architectural risk.
9. **Selection checkbox column** — last, the smallest independent piece; deferring let the renderer-touching items above iterate without breaking it.

All nine landed in a single session, with a Playwright gate per item and live verification in real Chromium via Chrome DevTools MCP — the lessons from v0.0.6 (where a WGSL reserved-keyword bug and a stale-callback closure both went undetected by jsdom-only CI) shaped the verification rhythm.
