# oneGrid v0.0.6 — Implementation Patterns Report

This report documents the implementation patterns the oneGrid v0.0.6 milestone should converge on for eight cross-cutting concerns. It is restricted to *patterns* — every recommendation is sourced from public W3C/WHATWG specs, MDN, RFCs, browser-engine bug trackers, and individual-engineer writing. No commercial data-grid source, prose, or trademark is referenced.

---

## 1. IME composition handling for cell editors

**Architecture.** Battle-tested editors treat IME as a state machine that runs *parallel* to the keyboard pipeline. A per-editor `composing` flag flips to `true` on `compositionstart`, is updated on every `compositionupdate`, and flips to `false` only on `compositionend` — and crucially, the editor never commits, navigates, or fires "Enter to save" while `composing` is true. `KeyboardEvent.isComposing` and the `keyCode === 229` sentinel are read defensively from `keydown`/`keyup` handlers, but the *authoritative* source of truth is the composition-event flag, because UA behaviour for `keydown` during composition diverges (Firefox added these events in 65, before that they were suppressed entirely) (https://bugzilla.mozilla.org/show_bug.cgi?id=354358). The W3C UI Events spec mandates that during a composition session `keydown`/`keyup` MUST still fire and MUST carry `isComposing=true`, with `compositionupdate` ordered after `beforeinput` but before `input` (https://www.w3.org/TR/uievents/).

The cell editor itself is a hidden contenteditable or `<input>` mounted in a DOM overlay; the canvas grid only receives "commit/cancel" callbacks. State derivation from composition events is preferred over `inputType==="insertCompositionText"` because Safari historically dispatched malformed `inputType` values during marked-text editing.

**Edge cases**
- `compositionstart` may fire *after* the first `keydown` of the trigger character; `compositionend` may fire *before* the closing `keydown` (https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionstart_event).
- macOS dead-key sequences (¨ + a → ä) generate composition events on Safari/Chrome but not on Firefox.
- Android Chrome dispatches `keydown` with `key="Unidentified"` and `keyCode===229` for *all* soft-keyboard input (https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing).
- iOS Safari shrinks the visual viewport but not the layout viewport when the on-screen keyboard appears, so `position:fixed` editor overlays disappear under the keyboard unless `visualViewport.offsetTop` is tracked (https://www.bram.us/2021/09/13/prevent-items-from-being-hidden-underneath-the-virtual-keyboard-by-means-of-the-virtualkeyboard-api/).
- `navigator.virtualKeyboard.overlaysContent = true` opts out of UA viewport resizing and exposes `keyboard-inset-*` env vars (https://developer.mozilla.org/en-US/docs/Web/API/VirtualKeyboard_API).
- Password managers (1Password, LastPass) inject DOM nodes into focused inputs, firing spurious `input` events that can be misread as composition output.
- Pasting during composition: `paste` fires before `compositionend` in some Chromium versions; the editor must queue the paste and apply it post-commit.

**Test strategy**
- Unit: dispatch synthetic `CompositionEvent("compositionstart"/"update"/"end")` with `data` payload to the editor host and assert state-machine transitions.
- Integration: drive the Chrome DevTools Protocol `Input.imeSetComposition` / `Input.insertText` commands from Playwright to simulate Pinyin/Hangul/Kana composition without a host IME (https://chromedevtools.github.io/devtools-protocol/tot/Input/).
- Browser: Playwright cross-browser matrix (Chromium/Firefox/WebKit) running fixtures that toggle `keyCode===229` paths.
- Mobile: Playwright Android emulation with `hasTouch:true` and a viewport-resize fixture that mimics the soft keyboard.

**Code surface in oneGrid**
`packages/core/src/editing/ime.ts` (state machine), `packages/core/src/editing/EditorOverlay.ts` (DOM positioning + visualViewport), `packages/core/src/editing/keymap.ts` (229 guard), `packages/adapters/react/src/CellEditorPortal.tsx`, `packages/adapters/svelte/src/CellEditor.svelte`, `packages/core/test/ime.cdp.spec.ts` (Playwright + CDP).

**References:** https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionstart_event · https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionend_event · https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing · https://www.w3.org/TR/uievents/ · https://bugzilla.mozilla.org/show_bug.cgi?id=354358 · https://developer.mozilla.org/en-US/docs/Web/API/VirtualKeyboard_API · https://www.bram.us/2021/09/13/prevent-items-from-being-hidden-underneath-the-virtual-keyboard-by-means-of-the-virtualkeyboard-api/ · https://chromedevtools.github.io/devtools-protocol/tot/Input/

## 2. Cell editor validation patterns

**Architecture.** Validation is layered: a synchronous *cell-level* validator runs on every `input` event (debounced ~100 ms); a *column-level* validator runs on commit; a *cross-cell* (row/sheet) validator runs after commit and may invalidate other cells. The editor exposes two outcomes — *reject-and-keep-open* (focus stays in the editor, `aria-invalid="true"` is set, an `aria-errormessage`-referenced element becomes visible) and *reject-and-revert* (the cell snaps back to its prior value, and a polite live region announces the failure). Async validators are wrapped with `AbortController` so each new keystroke aborts the previous request and only the most recent response is allowed to settle, eliminating the classic stale-response race (https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort).

ARIA semantics follow current screen-reader reality: `aria-invalid="true"` is toggled on the editor, `aria-errormessage` references the message node, and the message node carries `aria-live="polite"` because NVDA and VoiceOver still under-support `aria-errormessage` (https://adrianroselli.com/2023/04/exposing-field-errors.html). For blocking errors, a `role="alert"` element is preferred since it is equivalent to `aria-live="assertive"` + `aria-atomic="true"` (https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live).

**Edge cases**
- Setting `aria-invalid="true"` *before* the user has had a chance to type causes JAWS/VoiceOver to announce "invalid entry" on focus (https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA21.html).
- Combining `aria-live` on the error node with `aria-describedby` can cause "double-speak" in NVDA/JAWS.
- Async validation that completes after the user has navigated away — the result must be discarded, not surfaced on the wrong cell.
- Composition mid-validation: the validator must not run while `isComposing` is true, or it will reject partial codepoints.
- Cross-cell propagation can cycle (A invalidates B which invalidates A); a topological-pass cap is required.
- Browser autofill writes to the input *without* dispatching `input` in older WebKit; an `animationstart` listener on `:-webkit-autofill` is the standard workaround.

**Test strategy**
- Unit: run validators against fixture rows; assert AbortError handling for cancelled async requests.
- Integration: Vitest browser mode renders an editor and dispatches typing → assert `aria-invalid` toggling and live-region textContent.
- Screen-reader: Guidepup-driven NVDA + VoiceOver fixtures that capture spoken-phrase logs after a failing commit.

**Code surface in oneGrid**
`packages/core/src/validation/Validator.ts`, `packages/core/src/validation/AsyncRunner.ts` (AbortController), `packages/a11y/src/LiveAnnouncer.ts`, `packages/core/src/editing/CommitPolicy.ts`, `packages/adapters/{react,vue,svelte}/src/useValidation.*`.

**References:** https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-invalid · https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-errormessage · https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live · https://adrianroselli.com/2023/04/exposing-field-errors.html · https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort · https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA21.html

## 3. Custom cell renderers across framework adapters

**Architecture.** Because oneGrid renders cells to `<canvas>`, custom *DOM* renderers live in a *single overlay layer* sized to the viewport, and only cells whose visual area intersects the viewport are mounted. The proven pattern is an **object pool** keyed by renderer type: when a row scrolls in, a free instance is acquired, its props/inputs are updated reactively, and on scroll-out the instance is released back to the pool — analogous to Android's RecyclerView. This collapses allocation pressure and lets the GC stay quiet during fast scroll (https://gameprogrammingpatterns.com/object-pool.html). For lightweight markers (sparklines, badges) an `IntersectionObserver`-driven mount-on-visible scheme is sufficient and avoids manual virtualization math.

Reactivity is preserved by *not* tearing down framework state on recycle: React renderers stay mounted and only receive new props through a stable portal target; Svelte 5 components use `$state`-backed prop bindings so updates remain fine-grained (https://svelte.dev/blog/runes); Solid factory components set up signal subscriptions once and never re-execute, which is ideal for pooled reuse; Vue 3 composition-API renderers expose a `setProps()` imperatively. Microtask scheduling (`queueMicrotask`) batches per-frame prop updates so a 10k-row jump fires one render, not thousands.

**Edge cases**
- Pooled instances retain stale focus/selection state — must be reset on release, not on acquire.
- Framework devtools (React DevTools, Vue DevTools) report wildly inflated component counts unless pooled instances are kept under a stable parent.
- Solid components mounted once cannot accept reactive prop *replacement*; signals must be passed in as the prop and mutated.
- Portals allocated per cell defeat the pool; one portal per renderer-type, not per cell.
- IntersectionObserver `rootMargin` interacts badly with `transform`-based scroll containers — observer must be rooted to the actual scroll element.

**Test strategy**
- Unit: pool acquire/release invariants (size cap, reset hook called).
- Component: Vitest browser mode with `vitest-browser-react`/`-vue`/`-svelte` to assert renderers receive prop updates after recycle (https://vitest.dev/guide/browser/).
- Integration: Playwright scroll storms that assert peak DOM-node count stays bounded.
- Visual regression: Playwright screenshots of the overlay layer at fixed scroll offsets.

**Code surface in oneGrid**
`packages/core/src/render/RendererPool.ts`, `packages/core/src/render/OverlayLayer.ts`, `packages/adapters/react/src/CellRenderer.tsx` (createPortal), `packages/adapters/svelte/src/CellRenderer.svelte`, `packages/adapters/solid/src/CellRenderer.tsx`, `packages/adapters/vue/src/CellRenderer.ts`, `packages/adapters/angular/src/cell-renderer.directive.ts`.

**References:** https://gameprogrammingpatterns.com/object-pool.html · https://svelte.dev/blog/runes · https://vitest.dev/guide/browser/ · https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API

## 4. Set filter (distinct-values checkbox filter)

**Architecture.** Distinct enumeration is **lazy and incremental**: a streaming pass over the row source feeds a `Map<value, count>` hash set; the UI renders the first N distinct values immediately, then yields to `requestIdleCallback` between batches and updates a "1,234 of ~5,678" counter (the denominator is the row count, not a precomputed distinct count, since distinct cardinality is the thing being computed). For server-backed sources, the client offloads enumeration to the data provider via a documented adapter contract that maps to whatever the backend supports — SQL `SELECT col, COUNT(*) ... GROUP BY col`, OData's `$apply=groupby((col),aggregate($count as n))` (https://docs.oasis-open.org/odata/odata-data-aggregation-ext/v4.0/cs01/odata-data-aggregation-ext-v4.0-cs01.html), or GraphQL aggregate fields. Search-within-the-filter starts as substring (`String.prototype.includes` over the in-memory set) and graduates to a small fuzzy index (e.g. trigram or `Intl.Collator`-aware prefix) when the distinct set exceeds a threshold.

**Edge cases**
- Null vs empty-string vs missing-property must be three distinguishable buckets.
- Locale-sensitive equality — "Café" vs "Cafe" — needs `Intl.Collator` with `sensitivity:"base"` to match user expectations.
- Floating-point distincts collapse silently; numeric columns hash the formatted display value, not the raw float.
- Server pagination of distincts: the OData spec orders aggregation before `$skip`/`$top`, so the client can request distincts page-by-page.
- Counts go stale during async row updates; the filter must invalidate on data-source change events.

**Test strategy**
- Unit: streaming enumerator with synthetic 10M-row generators; assert memory cap and incremental yield.
- Property-based (fast-check): distinct-set equivalence vs `new Set(rows.map(...))`.
- Integration: mock OData/SQL adapter, snapshot the issued `$apply` string.
- Browser: Playwright drives the search box and asserts only matching checkboxes remain visible.

**Code surface in oneGrid**
`packages/core/src/filters/SetFilter.ts`, `packages/core/src/filters/DistinctEnumerator.ts`, `packages/core/src/data/adapters/odata.ts`, `packages/core/src/data/adapters/sql.ts`, `packages/core/src/i18n/Collator.ts`.

**References:** https://docs.oasis-open.org/odata/odata-data-aggregation-ext/v4.0/cs01/odata-data-aggregation-ext-v4.0-cs01.html · https://learn.microsoft.com/en-us/odata/client/grouping-and-aggregation

## 5. Floating filters

**Architecture.** Floating filters live in a **second header row** within the same CSS grid as the main header, using `grid-template-rows: auto auto` and `position: sticky; top: var(--header-h)` so they stay pinned during vertical scroll. Horizontally, frozen columns are a separate sticky band that participates in the same grid via `position: sticky; inset-inline-start: 0`. The filter row composes per-column inputs (text, range, set-popover trigger) and is wrapped in `role="toolbar"` with `aria-label`, plus `aria-controls` pointing at the grid id. Keyboard navigation follows the WAI-ARIA toolbar pattern: a single tab stop into the row, then Left/Right arrows rove focus among the inputs using the standard `tabindex="0"`/`tabindex="-1"` swap (https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/, https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/).

**Edge cases**
- The toolbar guidance warns against arrow-key-consuming controls (text inputs, sliders) inside roving toolbars; the pragmatic compromise is to route arrow keys to the input only when the input has internal selection, otherwise to the toolbar — and document the exception.
- Frozen columns paired with a horizontal scrollbar in the floating row cause "double scroll" on Safari unless the frozen band is taken out of the scroll container.
- Sticky positioning fails inside `transform`-ed ancestors; the grid root must not be transformed.
- A column resize must reflow the floating filter without losing focus — store focused-column id, restore after layout.
- Disabled filter inputs must remain focusable per APG keyboard-interface guidance, otherwise screen-reader users miss them.

**Test strategy**
- Unit: roving-tabindex reducer; arrow keys mutate the focus index correctly with wrap/no-wrap modes.
- Browser: Playwright keyboard sequence asserts focus order matches DOM order under both LTR and RTL.
- Visual: fixed-viewport screenshots with frozen column + active floating filter.
- A11y: axe-core check that the toolbar has an accessible name.

**Code surface in oneGrid**
`packages/core/src/header/FloatingFilterRow.ts`, `packages/core/src/header/StickyLayout.ts`, `packages/a11y/src/RovingTabindex.ts`, `packages/adapters/*/src/FloatingFilter.*`.

**References:** https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/ · https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/ · https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/toolbar_role

## 6. Tooltip system

**Architecture.** A **single shared tooltip element** is kept in the document and re-targeted per cell, eliminating per-cell DOM allocation. Positioning uses Floating UI's middleware composition — `offset` first, then `flip` (with `crossAxis: "alignment"` and a `fallbackAxisSideDirection`), then `shift({ padding })`, optionally `size` for viewport-clamped tooltips, and `arrow` last (https://floating-ui.com/docs/middleware, https://floating-ui.com/docs/flip, https://floating-ui.com/docs/shift, https://floating-ui.com/docs/size). When the build target is evergreen, the implementation can fall back to native CSS Anchor Positioning (`anchor-name` / `position-anchor` / `position-try-fallbacks`) for zero-JS positioning (https://www.w3.org/TR/css-anchor-position-1/, https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning). The tooltip element uses the Popover API (`popover="hint"`) so it participates in the top layer and gets browser-managed light dismiss without focus-trapping (https://developer.mozilla.org/en-US/docs/Web/API/Popover_API).

Semantics: `role="tooltip"` plus `aria-describedby` from the trigger; never `role="dialog"` for plain tooltips because tooltips must not contain interactive content (https://hidde.blog/popover-semantics/). A 500–700 ms hover delay matches platform conventions; touch users get the tooltip via long-press or a separate "info" affordance.

**Edge cases**
- `flip` and `autoPlacement` cannot coexist — pick one (https://floating-ui.com/docs/flip).
- Tooltip clipped by an overflow-hidden ancestor: switch boundary to the viewport or use the top-layer popover.
- Hover-intent: the tooltip must stay open while the pointer moves between trigger and tooltip — implemented by listening on both elements with a shared timer.
- WCAG 1.4.13 requires the tooltip be dismissable with Escape, hoverable, and persistent until dismissed/blurred.
- Anchor positioning ignores `display:none` anchors; the trigger must remain in layout.

**Test strategy**
- Unit: Floating UI middleware integration with a mocked DOM rect.
- Browser: Playwright hover at viewport edges to assert flip; resize fixtures for `size` middleware.
- A11y: axe-core + a fixture asserting `aria-describedby` linkage and Escape dismissal.

**Code surface in oneGrid**
`packages/core/src/tooltip/Tooltip.ts` (singleton element), `packages/core/src/tooltip/position.ts` (Floating UI), `packages/core/src/tooltip/anchor.css` (CSS anchor fallback), `packages/a11y/src/describedBy.ts`.

**References:** https://floating-ui.com/docs/middleware · https://floating-ui.com/docs/flip · https://floating-ui.com/docs/shift · https://floating-ui.com/docs/size · https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning · https://www.w3.org/TR/css-anchor-position-1/ · https://developer.mozilla.org/en-US/docs/Web/API/Popover_API · https://hidde.blog/popover-semantics/

## 7. @onegrid/migrate CLI (config translator)

**Architecture.** The migrator is an AST-based source rewriter, not a regex tool. Three viable engines exist: **jscodeshift** (jQuery-like API over recast, mature codemod ecosystem; https://www.npmjs.com/package/jscodeshift), **ts-morph** (high-level TypeScript Compiler API wrapper, type-aware; ideal when migrations need to read inferred types), and **Babel** plugins (preserves formatting via `@babel/parser` + recast, lowest barrier when the team already maintains Babel plugins). For oneGrid we recommend **jscodeshift as default with ts-morph for type-driven cases** — jscodeshift handles JSX/TSX uniformly and parallelises across files, while ts-morph's symbol resolution is invaluable when a translation depends on a column-definition's element type.

Mapping policy splits into **mechanical 1:1 prop renames** (table-driven) and **semantic translations** (custom transformer per source key). When a translation is ambiguous or lossy, the AST visitor inserts a leading-comment node `// TODO(@onegrid/migrate): review — <reason>` so the diff is self-documenting. The CLI is built on **oclif** for command structure and **Ink** for the interactive diff/dry-run UI (https://oclif.io/docs/introduction/) — `migrate --dry-run` prints colorized diffs without writing, `migrate --apply` writes, and `migrate --only <glob>` allows partial application. **Clean-room rule:** translators are written *only* against publicly described configuration shapes documented on third-party project websites; no source code, type definitions, or non-public docs are consulted, and this is enforced by a `CONTRIBUTING.md` provenance checklist on every new mapping.

**Edge cases**
- Spread operators (`{...userConfig}`) defeat naive prop renames — the visitor must bail out with a TODO.
- Computed property keys (`{[key]: ...}`) cannot be statically rewritten.
- Type-only imports must be rewritten without leaving runtime cruft.
- Mixed JS/TS/TSX projects need parser-per-file selection.
- Recast can lose formatting around unmodified nodes if intermediate parents are replaced — modify in place.

**Test strategy**
- Golden-file fixtures: `__testfixtures__/<case>.input.tsx` → `<case>.output.tsx` consumed by `jscodeshift/dist/testUtils.defineTest`.
- Snapshot tests for the CLI's stdout under `--dry-run` (Vitest snapshot).
- E2E: spawn the built CLI against a sample project repo and assert exit code + diff.

**Code surface in oneGrid**
`packages/migrate/src/cli.tsx` (oclif + Ink), `packages/migrate/src/transforms/*.ts` (per-source transformers), `packages/migrate/src/policy/renameTable.ts`, `packages/migrate/__testfixtures__/`, `packages/migrate/src/util/comment.ts`.

**References:** https://www.npmjs.com/package/jscodeshift · https://github.com/facebook/jscodeshift (via npm page) · https://oclif.io/docs/introduction/ · https://github.com/vadimdemedes/ink

## 8. Accessibility conformance suite for canvas grids

**Architecture.** The grid's overlay DOM mirrors WAI-ARIA 1.2 grid semantics: `role="grid"` on the root with `aria-rowcount` / `aria-colcount` reflecting *total* (virtualised) counts, `role="row"` on each rendered row carrying `aria-rowindex`, and each `role="gridcell"` carrying `aria-colindex` (https://www.w3.org/WAI/ARIA/apg/patterns/grid/, https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/). When a custom framework renderer is mounted into a cell, the cell DOM node retains `role="gridcell"` and the framework component renders *inside* it — the cell must remain semantically a cell, never be replaced by an arbitrary widget root, since `aria-owns` reordering is poorly supported and breaks reading order. Focus management uses `aria-activedescendant` on the grid root, with the active cell receiving a visible focus indicator and being scrolled into view (https://www.w3.org/WAI/ARIA/apg/patterns/grid/examples/data-grids/).

CI runs three layers. Layer 1: **axe-core via @axe-core/playwright** for static violations against WCAG 2.1 A/AA tags (https://playwright.dev/docs/accessibility-testing). Layer 2: **accessibility-tree snapshots** via Playwright's `page.accessibility.snapshot()` and the newer `locator.ariaSnapshot()`/`page.ariaSnapshot()`, comparing structured YAML against goldens. Layer 3: **screen-reader smoke tests** via Guidepup, which drives NVDA on Windows and VoiceOver on macOS through a single API and exposes `spokenPhraseLog()` (https://www.guidepup.dev/, https://github.com/guidepup/guidepup). JAWS automation remains limited; oneGrid documents JAWS as a manual-only target.

**Edge cases**
- Virtualised rows must report `aria-rowindex` based on the *logical* index, not the DOM index.
- Inconsistent `aria-colindex` values can make screen readers skip cells (https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/).
- When `aria-readonly` is set on the grid, it propagates to all cells — overrides must be explicit per-cell.
- Custom renderers that capture focus inside the cell break grid arrow-key navigation; focus trapping must be opt-in.
- VoiceOver on Safari announces "invalid data" only when `aria-invalid` is set after blur, not on mount.

**Test strategy**
- Static: `@axe-core/playwright` with `withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa'])`.
- Tree: `expect(await page.ariaSnapshot()).toMatchSnapshot()`.
- Screen-reader: Guidepup-Playwright fixture asserting NVDA speaks "row 5 column 3 …" after arrow navigation.
- Conformance: a script asserting `aria-rowcount`/`aria-colcount` invariants over property-based fixtures.

**Code surface in oneGrid**
`packages/a11y/src/GridSemantics.ts`, `packages/a11y/src/ActiveDescendant.ts`, `packages/a11y/src/__tests__/axe.spec.ts`, `packages/a11y/src/__tests__/aria-snapshot.spec.ts`, `packages/a11y/src/__tests__/guidepup.{nvda,voiceover}.spec.ts`, `packages/core/src/render/CellAriaAdapter.ts`.

**References:** https://www.w3.org/WAI/ARIA/apg/patterns/grid/ · https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/ · https://www.w3.org/WAI/ARIA/apg/patterns/grid/examples/data-grids/ · https://playwright.dev/docs/accessibility-testing · https://www.guidepup.dev/ · https://github.com/guidepup/guidepup

## Critical-path implementation order

Ship in this sequence:

**1. Accessibility conformance suite (Section 8)** — first, because ARIA grid semantics underlie every other surface and are nearly impossible to retrofit. Wiring `aria-rowindex`/`aria-colindex`/`aria-activedescendant` after renderers and editors exist forces invasive rewrites.

**2. IME composition handling (Section 1)** — second, because the editor depends on it; the 229-keydown problem is silent in English-locale CI and surfaces only when CJKT users hit production.

**3. Cell editor validation (Section 2)** — third, sitting on top of (1) and (2). `aria-invalid`/`aria-errormessage` plumbing reuses the live-region work from Section 8.

**4. Custom cell renderers (Section 3)** — fourth, once editing is stable. The renderer pool is the most complex non-a11y subsystem; deferring lets adapter teams parallelise.

**5. Tooltip system (Section 6)** — fifth; depends on a11y describedby plumbing and is needed by validation error UI.

**6. Floating filters (Section 5)** and **7. Set filter (Section 4)** — paired; the toolbar a11y plumbing is shared, and set-filter UX needs the floating row to live in.

**8. @onegrid/migrate CLI (Section 7)** — last. Migration value is proportional to API stability; shipping it before 1–7 settle would force the migrator to rewrite itself.
