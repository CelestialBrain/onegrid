# v0.1.0 — "WebGPU rendering"

**Status:** all 6 items shipped (scaffold + protocol; full
canvas→WebGPU renderer migration lands as v0.1.0.x patches on the
infrastructure this milestone establishes).

**Date:** 2026-05-16

The flagship moonshot, taken honestly. v0.1.0 ships:

- the **scaffolding** every WebGPU renderer needs (device acquisition,
  swap-chain wiring, cell-quad pipeline, MSDF text shader, per-cell
  vertex buffer protocol)
- the **compute extensions** that compose with the renderer (GPU
  hash-aggregate joining v0.0.10 item 7's group-by;
  viewport-scale sort/filter via the existing v0.0.5 kernels)
- the **cross-source SQL join** capability (`@onegrid/duckdb-join`)

What v0.1.0 does NOT ship: the actual port of `@onegrid/core`'s canvas
renderer to WebGPU. That's a v0.1.0.x patch series — the contracts are
locked, the migration soaks in real apps before it's promoted.

## Critical-path sequencing

1. **Per-cell vertex buffer protocol** — 32-byte interleaved Cell
   struct + 16-byte Glyph entries. The wire format every other piece
   builds on.
2. **MSDF atlas + WGSL snippet** — text rendering primitive. Lands
   second because the cell pipeline references it.
3. **`createRenderScaffold(canvas)`** — device + swap chain + cell
   pipeline. Composes items 1 + 2.
4. **GPU hash-aggregate** — atomic-add into a power-of-two-bucketed
   hash table on the GPU. The hard part: WGSL has no `atomic<f32>`,
   so float accumulation runs through a `bitcast` + `atomicCompareExchangeWeak`
   spin loop.
5. **Compute sort/filter at viewport scale** — caller-concern shape
   over the existing v0.0.5 kernels. Documented; no new code.
6. **Cross-DB joins via DuckDB-WASM** — `@onegrid/duckdb-join`. Three
   source kinds (rows, arrow bytes, inline SQL); register → query →
   unregister bundled in one `executeJoinQuery` helper.

## Per-item

### 1. Per-cell vertex buffer protocol

Every visible cell packs into one Float32 interleaved vertex buffer.
The vertex shader treats each cell as an instance and emits a quad
via `vertex_index 0..5`. Cell stride: **32 bytes**; glyph stride:
**16 bytes**:

```
offset  attribute            kind     notes
  0     x_top_left           f32      viewport-space pixel
  4     y_top_left           f32
  8     width                f32
 12     height               f32
 16     bg_color (rgba)      u32      packed; vertex shader unpacks
 20     fg_color (rgba)      u32
 24     glyph_atlas_start    u32      index into glyph-run buffer
 28     glyph_count          u32
```

Glyphs live in a secondary buffer indexed via
`glyph_atlas_start + glyph_count`. A 5-character cell pays
~16 bytes/glyph instead of duplicating the cell rect.

`packCells()` packs CPU-side; the result is two `ArrayBuffer`s ready
for `device.createBuffer({ usage: VERTEX | STORAGE })`.

### 2. MSDF glyph atlas + WGSL snippet

Multi-channel signed distance field text. Atlas JSON follows the
public `msdf-bmfont-xml` / `msdf-atlas-gen` standard layout. The
`MSDF_WGSL` snippet exports three helpers:

```wgsl
fn msdf_median(rgb: vec3f) -> f32 { ... }
fn msdf_distance(rgb: vec3f) -> f32 { ... }
fn msdf_alpha(distance: f32, px_range: f32) -> f32 { ... }
```

Embed `${MSDF_WGSL}` inside your fragment shader and call
`msdf_alpha(msdf_distance(textureSample(atlas, samp, uv).rgb), screen_px_range)`.
`screen_px_range` is the per-frame ratio of atlas pixels to screen
pixels:

```ts
import { screenPxRange } from '@onegrid/webgpu-render';
const uniform = screenPxRange(atlas, currentEmPxOnScreen);
```

We don't ship the offline baker — use `msdf-bmfont-xml` or
`msdf-atlas-gen`; both produce JSON in the shape this package expects.

**Reference:** Viktor Chlumský, *Shape Decomposition for Multi-Channel
Distance Fields* (master's thesis, 2015) — the public algorithm
every MSDF implementation derives from.

### 3. `createRenderScaffold(canvas)`

Device acquisition (shared via `@onegrid/webgpu`'s `getDevice()`
cache so the compute kernels and render pipeline use ONE GPUDevice),
swap-chain configuration with `alphaMode: 'premultiplied'`, and a
solid-color cell-quad pipeline built from the vertex buffer protocol.

Throws `[OG_WEBGPU_UNAVAILABLE]` when `navigator.gpu` is missing —
callers fall back to the canvas renderer at the `@onegrid/core` layer
without taking a runtime dependency on `@onegrid/webgpu-render`.

### 4. GPU hash-aggregate kernel

```
gpuHashAggSumF32(keys: Uint32Array, values: Float32Array, { numBuckets? }) →
  { bucketKeys, bucketSums, bucketCounts }
```

Each thread atomically updates the bucket selected by `key & (numBuckets - 1)`.
Float accumulation runs through a `bitcast<u32>(f32)` + `atomicCompareExchangeWeak`
spin loop because WGSL has no `atomic<f32>`.

**Constraints:**
- `numBuckets` must be a power of two (mask-based bucketing).
- Collision policy: both keys' contributions land in the same slot.
  Linear-probing is intentionally NOT shipped in v0.1.0 — adopters
  pick `numBuckets ≥ 4× expected group cardinality` to keep load
  factor low.
- The CPU fallback `cpuHashAggSumF32` is the correctness oracle —
  identical signature, exact `Map`-based grouping.

5 unit tests on the CPU oracle. The GPU kernel itself runs in real
Chromium (skipped in this session's headless suite because no GPU).

### 5. Compute sort/filter at viewport scale

The existing v0.0.5 kernels (`gpuSumFloat32`, `gpuFilterMaskF32`)
already cover this. "Viewport scale" is a caller-side discipline:
slice the column vector to the visible range before dispatch.

Documented pattern:

```ts
const visibleSlice = columnValues.subarray(firstVisibleRow, lastVisibleRow);
const mask = await gpuFilterMaskF32(visibleSlice, 'gte', 100);
// mask covers ONLY the visible rows; the off-screen rows pay zero GPU cost
```

This composes cleanly with the v0.0.10 column virtualization — the
GPU sees ~30 cells × M columns instead of N rows × M columns.

### 6. Cross-database joins via DuckDB-WASM

`@onegrid/duckdb-join` registers heterogeneous sources as DuckDB
views; one SQL query joins across them inside the browser.

Three source kinds:

| Kind    | Use when                                                  |
| ------- | --------------------------------------------------------- |
| `rows`  | ≤ 1k JS objects. Emits a `VALUES (...)` inline view.       |
| `arrow` | Larger source. `db.registerFileBuffer` + `read_arrow()`.   |
| `sql`   | An inline SELECT / VALUES wrapped as the view body.       |

```ts
const result = await executeJoinQuery({
  db,
  sources: [
    { kind: 'rows', name: 'orders', rows: ordersFromPostgres },
    { kind: 'rows', name: 'customers', rows: customersFromMongo },
    { kind: 'sql',  name: 'events', query: 'VALUES (1, 7), (2, 12)' },
  ],
  query: `
    SELECT o.id, o.total, c.name, e.count
    FROM orders o
    LEFT JOIN customers c ON o.customer_id = c.id
    LEFT JOIN events    e ON o.customer_id = e.column1
    LIMIT 100
  `,
});
```

The signature use case: **orders from Postgres LEFT JOINed with
customer profiles from MongoDB LEFT JOINed with event counts from
ClickHouse**, all reconciled in the browser in the same render frame.
No other open-source grid ships this.

`@duckdb/duckdb-wasm` is an optional peer — adopters who already
integrate DuckDB-WASM (the v0.0.8 `@onegrid/duckdb` adapter) bring
their own `AsyncDuckDB` instance.

8 unit tests on the SQL generation. Real-Chromium DuckDB integration
lives in `apps/benchmarks` (cold `AsyncDuckDB` boot takes 1+ s, out
of unit scope).

## Deferred to v0.1.0.x

These are the items that need the contracts from v0.1.0 to soak
before they're promoted:

- **Canvas renderer → WebGPU renderer migration.** The actual port
  of `@onegrid/core`'s canvas paint loop to use `createRenderScaffold`
  + `packCells` + MSDF text. Will land as
  `@onegrid/core/features/webgpu-render` behind a sub-path import,
  budgeted via the v0.0.9 per-feature bundle gate.
- **MSDF cell-renderer overlay refactor.** Move React fiber +
  custom-renderer cells off the DOM overlay and onto the GPU text
  pipeline. Big win for scroll perf at high custom-renderer density.
- **Hash-agg linear probing.** Drops the "pick numBuckets ≥ 4×
  cardinality" constraint; works for unknown-cardinality joins.
- **Slug-style per-curve text** for arbitrary zoom (atlas-free
  fallback). Lower priority than the MSDF path; lands when high-zoom
  use cases surface.
- **WebGPU benchmark suite** — 100 visible cells × 10M rows scroll
  at 60 FPS as the gate before the canvas→WebGPU migration ships
  the default.

## What this milestone changes

Before v0.1.0, the canvas renderer was the only render path. The
MSDF fragment shader, the cell-quad pipeline, and the per-cell
vertex buffer were one-off snippets in branches. After v0.1.0:

- The **protocol** for getting cells onto the GPU is stable and
  versioned.
- The **MSDF atlas format** is a public contract — adopters can pre-
  bake their own fonts with off-the-shelf tooling and drop them in.
- The **GPU hash-aggregate** kernel composes with v0.0.10 item 7's
  group-by operator algebra, so a grouped DBSP plan can drop the
  CPU reduction step on supported hardware.
- The **cross-source SQL join** capability lands the second-most-
  cited differentiator from the roadmap (after the live ORM sync
  from v0.0.11).

The full canvas→WebGPU paint-loop migration is the v0.1.0.x story.
What we shipped in v0.1.0 is the protocol that migration plugs into.
